推荐算法及应用
六次综合实验指导书

基于 Spark 与 AI 增强的电影个性化推荐系统。围绕真实数据、真实推荐算法与可运行的系统，以团队协作完成整个项目。

6 次完整实验单元
24 课时全部任务在课堂内完成
3–5 人每组一个 GitHub 私有仓库

统一约定（六次实验不再重复）

  • 数据版本：rec-course-v3-train5-1.0.0；划分版本：temporal-v1-cold500-train5-v3。课堂目录 8,459 部电影；固定评价训练 583,502 条、验证 70,366 条、测试 67,792 条。
  • 算法范围：基础版必做热门推荐、内容推荐、ItemCF、Spark ALS、冷启动及 Precision@10、Recall@10。UserCF 不要求实现。
  • 数据隔离：离线评价只使用冻结的 evaluation/train.csv 拟合；validation.csv 用于调参与检查，test.csv 只在方案固定后用于最终报告。不可把 business 库的完整历史评分用于离线评价训练。历史用户 ml:<id> 与注册用户 app:<id> 不得混用。
  • 统一评价：正反馈为评分 ≥4.0；Top-10 排除协议指定的已评分电影；使用教师固定评价用户集合及候选目录；无结果和不足 10 条的用户不得被悄悄移除。基础版至少报告 Precision@10 与 Recall@10，不设必须超过其他算法的分数门槛。
  • AI 使用方法：理解工程与约束 → 自行拆分目标和制定计划 → 逐项实现 → 自检与定位错误 → 接入系统并复核。教师不提供可复制的开发提示词；学生对 AI 生成代码和结果负责。
  • 交付形式：每组维护一个GitHub私有仓库，每次课结束前完成一次阶段提交与推送，并现场展示运行结果及测试证据；不要求六篇实验报告。第六次统一提交项目仓库、模型、评价表、简要技术说明和成员贡献记录。不安排课外补交或额外开发任务。
  • 发行边界：离线运行镜像用于快速搭建基础系统；学生后续实现算法、修改前端属于自行开发任务，可能需要联网重建镜像。教师不承诺完整断网开发构建，也不要求安装或测试阶段B离线构建依赖包。
  • 环境与协作：Windows系统检查、离线镜像导入、Starter Kit初始化见附录A及随包独立《Windows实验环境安装与启动指南》；GitHub建库和每次推送见附录B；公网部署见附录C（挑战版选做）。所有工作均在课堂内进行。
  • 基础自检：通过教师发行包的诊断入口核查数据库、接口契约与冻结评价输入；学生算法还须提供真实的推荐结果和评价证据。Windows/Docker启动与源码更新以随包对应版本的操作说明为准。不得以协议测试通过冒充推荐效果达标。

实验一　系统认知、基于内容的推荐与界面个性化（4 课时）

1. 实验目标

了解现有推荐系统的前后端与算法接口；利用电影类型特征实现真实的基于内容的个性化推荐；完成小组自己的第一处前端变化。

2. 必要原理

  • 内容表示：将 genres 转换为多维电影特征（如 Multi-hot 或 TF-IDF）。
  • 内容相似：余弦相似度衡量候选电影与用户兴趣画像的相近程度。
  • 用户画像：根据该用户允许使用的历史正反馈聚合兴趣，排除已评分电影；无有效画像时不能伪称已有个性化结果。
  • 工程关系：前端 → FastAPI 推荐路由 → 学生 Provider → 真实电影 Top-N。

3. 实验任务

  1. 参照附录A完成Docker检查、离线镜像导入、Starter Kit首次初始化或日常启动；参照附录B建立小组私有仓库；检查电影浏览、历史用户与现有推荐API，定位算法接入契约。
  2. 使用真实电影类型与用户历史记录，完成 content 推荐，输出最多 10 部可解释的电影；不使用随机或固定电影列表。
  3. 将算法接入现有推荐接口，并通过真实API响应及可操作页面展示结果。当前发行候选的“推荐实验室”可能仍是占位页，学生需在课堂内自主完善展示交互；未完成时继续保持 501，不用假数据掩盖。
  4. 在课堂内完成至少一项明显可见的前端个性化修改（视觉风格、实质布局或有效交互任选一种），保留所有既有业务能力。

4. 验收标准

  • 系统能启动；所用电影与用户ID真实且命名空间正确。
  • 至少一个有有效历史正反馈的历史用户可得到合法 Top-10；无重复、无已评分电影、排名与分数可追溯。
  • Provider 自检和接口调用成功；能口头说明两部电影为何内容相近。
  • 展示一处真实前端改动，页面仍可完成原有业务操作。

5. 成果要求

内容推荐代码及模型/特征工件、一次自检记录、实际推荐页面、前端修改对比；本次GitHub提交与推送记录。课堂内验收。

实验二　新用户冷启动与 ItemCF（4 课时）

1. 实验目标

解决用户没有历史行为时的推荐入口；实现基于物品的协同过滤，并理解内容相似与行为共现的差异。

2. 必要原理

  • 冷启动：没有评分时使用热门榜单或主动收集偏好；有少量评分后可使用内容或物品邻居产生候选。
  • ItemCF：由用户—电影交互构造共现与电影相似度，基于用户喜欢的电影汇总候选得分。
  • 数据稀疏性：低共现支持会影响相似度可靠性；推荐必须排除用户已评分电影。

3. 实验任务

  1. 基于训练数据计算可解释的热门榜单，避免只按极少量高分排序。
  2. 为新注册账号设计可操作的冷启动入口：无评分也能得到非个性化结果；选择偏好或产生评分后能体现选择/行为的作用。界面标明推荐策略。
  3. 实现 itemcf 的电影相似度与个性化 Top-10，并接入推荐实验室；自行确定合理的邻居与低支持度处理方法。
  4. 对同一历史用户展示内容推荐和 ItemCF 的结果差异，并解释一个真实推荐案例。

4. 验收标准

  • 新账号零评分时可得到明确来源的推荐，不能把热门榜单标成个性化结果。
  • 新用户产生有效偏好或评分后有可验证的推荐变化，或明确说明尚不能个性化的原因。
  • ItemCF 基于真实训练交互，结果无重复且排除已评分电影；至少一个历史用户正常出结果。
  • 能说明 ItemCF 与基于内容推荐分别依赖什么数据。

5. 成果要求

热门、冷启动与 ItemCF 实现及模型工件，前端演示结果，自检/测试记录及本次GitHub推送。课堂内验收。

实验三　Spark ALS、算法评价与基础版检查（4 课时）

1. 实验目标

理解 LFM 与 ALS 的关系；运行 Spark ALS 并生成真实 Top-10；以同一评价协议比较经典算法。

2. 必要原理

  • LFM 将用户、电影映射为隐向量，以内积预测评分；ALS 通过交替最小二乘求解隐向量。
  • 评分预测与Top-N排序目标不相同；模型可以正常训练却得到较低的推荐命中率。
  • Precision@10、Recall@10 需要明确相关性阈值、候选过滤和固定评价用户。

3. 实验任务

  1. 使用冻结的 train 完成 Spark MLlib ALS 显式评分训练，保留真实模型、参数及版本清单；生成指定历史用户的 Top-10 并接入已有接口。
  2. 为 Popular、Content、ItemCF、ALS 按统一协议产出 validation 的 Precision@10 和 Recall@10；记录有效用户数及推荐覆盖情况。
  3. 对比四种方法的结果，给出至少两条依据真实数据的解释；不允许根据 validation/test 正例直接拼凑推荐列表。
  4. 集中检查基础版功能是否完整；课堂剩余时间用于修复基础算法及系统接入问题。

4. 验收标准

  • ALS 使用真实 Spark 训练，模型版本与数据摘要一致；历史用户的结果合法并排除已评分电影。
  • 提交四方法的真实比较表，指标计算方式一致；无结果用户未被剔除。
  • 能说明 LFM/ALS 关系、评分预测与Top-N效果的区别；不能以“ALS必须优于ItemCF”为达标条件。
  • 基础版能够展示内容、ItemCF、ALS、热门及冷启动策略。

5. 成果要求

ALS 模型及清单、真实推荐结果、统一算法评价表、简短结果分析、基础版检查记录及本次GitHub推送。课堂内预验收。

实验四　现代推荐系统扩展开发（一）（4 课时）

1. 实验目标

从标准扩展中选择两项，完成第一项能够独立验收的真实功能。

2. 必要原理

  • S1 加权RRF：对不同算法返回的名次进行融合，不能直接混加不同量纲的原始分数。
  • S2 LLM工具调用：模型负责解析自然语言并选择受控工具；电影查询与推荐结果必须来自真实业务接口。
  • S3 Kafka事件驱动：前端行为 → 事件消息 → 消费端更新短期兴趣 → 后续推荐改变；接收到消息不等于已实现实时推荐。

3. 实验任务

  1. 小组在课堂内确定 S1/S2/S3 中的两项（标准版三选二），明确负责人和验收证据。
  2. 实现第一项，最低要求如下：
    • S1：融合至少两路真实候选，去重、过滤、排序，并显示推荐来源及名次。
    • S2：自然语言意图解析＋结构化输出＋实际 Function Calling；返回数据库中真实电影并说明依据，使用外部模型API，不部署或微调模型。
    • S3：真实评分/收藏产生Kafka事件；消费端更新可追溯的短期兴趣，并使后续推荐发生规则明确的变化。
  3. 运行真实功能测试，排查与现有登录、推荐API的集成问题。

4. 验收标准

  • 所选扩展可完成一个真实端到端演示，不接受静态页面、Mock或随机结果。
  • S1能追溯来源，S2能检查工具调用和电影ID真实性，S3能追踪事件、状态及推荐变化。
  • 原基础版功能无回归问题。

5. 成果要求

第一扩展模块源码、真实操作演示、最少一项正常与一项异常测试证据及本次GitHub推送。课堂内验收。

实验五　现代推荐系统扩展开发（二）（4 课时）

1. 实验目标

完成第二项标准扩展，并将两项扩展与已有推荐流程集成，形成具有小组特色的系统。

2. 必要原理

复习小组选用的第二项模块的输入、输出和失败处理；理解扩展技术的价值必须由行为变化、真实调用或可复现结果证明，而不是由技术组件名称证明。

3. 实验任务

  1. 按实验四同一标准实现第二项扩展（S1/S2/S3三选二，不新增必做技术）。
  2. 联调两项扩展与基础推荐系统；完善必要的前端交互与状态反馈，使小组作品具备可辨识的特点。
  3. 开展正常、无结果、错误输入或外部服务不可用等场景测试，并保留证据。
  4. 若基础版尚未完成，本次应优先修复核心算法与评价，不要求用扩展功能掩盖基础功能缺失。

4. 验收标准

  • 两项扩展分别能够真实运行并说明用途；基本输入输出与权限约束正确。
  • 已实现功能具有明确错误或无结果状态，不能静默伪造数据。
  • 系统基本操作与三种核心算法保持可用；能够解释至少一项扩展与经典推荐的关系。

5. 成果要求

两项标准扩展的源码及测试、联调界面、关键技术说明及本次GitHub推送。课堂内验收。

实验六　系统集成、项目展示与个人答辩（4 课时）

1. 实验目标

完成系统集成检查、统一成果提交和个人技术答辩，证明推荐功能真实、工程可以复现。

2. 必要原理

完整推荐链路：数据与用户行为 → 模型/候选 → 推荐接口 → 过滤排序 → 前端结果；区分“系统运行成功”“算法正确”“效果良好”三种判断。

3. 实验任务

  1. 检查环境启动、注册评分收藏、历史用户演示、三个核心算法、热门与冷启动、评价结果及小组界面改造。
  2. 展示所完成的标准扩展；挑战版团队展示全部三项标准扩展及一项真实有效的创新。
  3. 提交最终项目与简短技术说明（结构、数据版本、模型参数、评价表、测试证据、成员分工及AI协作中关键决策）。
  4. 每位成员参加现场答辩；教师可随机指定用户、算法或常见异常进行检查。

4. 验收标准

  • 推荐和指标真实、可复现，不存在用测试标签拟合、伪造结果或把历史匿名用户当真实账号的情况。
  • 基础版包含三种核心算法、热门、冷启动与评价；标准版在此基础上实现S1/S2/S3至少两项；挑战版完成三项并有可验证创新。
  • 界面具有至少一项实质变化，原有业务功能保持可用。
  • 学生能够指出相关代码、输入输出、关键参数和真实故障处理方式，而非只演示AI生成页面。

5. 成果要求

最终可运行项目、真实模型与指标、测试记录、简要成果说明、最终GitHub仓库地址和全员现场答辩；本次课堂内完成最终提交。

附录A　Windows环境与离线Starter Kit（课堂内必做）

适用范围：首轮为Windows x64、Docker Desktop（WSL2后端）、Linux/amd64镜像。不要求额外安装Ubuntu，不要求在宿主机安装MySQL、Node或Python才能启动教师提供的基础网站。具体版本要求以学生发行包内《Windows实验环境安装与启动指南》为准。

A1. 首次使用顺序

  1. 检查Windows版本、硬件虚拟化、WSL2、Docker Desktop与磁盘空间，确保Docker Engine处于Linux容器模式。已有Docker的电脑不要重复安装WSL；有其他课程项目时先核对项目、端口和数据卷。
  2. 将教师提供的同一发行版本完整学生包解压到本人可写目录，找到同时包含compose.yaml、deployment、data的项目根目录。不要用旧版Starter Kit脚本替换新包工具。
  3. 使用发行包内的校验工具检查文件和镜像归档，按《学生快速开始》先运行离线镜像导入，再运行首次初始化；第一次导入镜像不等于已建数据库。
  4. 初始化成功后启动网站，用浏览器访问启动工具实际显示的网址（默认http://127.0.0.1:8080），完成电影查询、注册登录、评分和收藏检查。初始化后只有MySQL处于运行状态、网站尚未启动，是正常现象。
  5. 每次上课通过发行包的启动工具打开网站，下课使用停止工具；不要反复初始化。保存项目源码和小组Git提交。

学生优先使用发行包内的BAT入口；如电脑安全管理已明确允许、但CMD受限，才按详细指南使用对应PowerShell备用入口。不为完成实验自行解除安全策略、重置WSL或删除Docker数据卷。

A2. 修改源代码后的操作边界

教师离线运行包已验证的是导入镜像、数据库初始化、业务运行和停启持久化，不是完全离线的源码构建环境。修改Python推荐算法或Vue源码后，必须使用最终发行包实际提供的代码更新/构建方法；可能需要联网安装构建依赖。单纯保存源码、刷新网页或重启容器，不保证新代码已进入镜像。

如果发行包尚未提供经实际验收的自动构建入口，学生应在课堂内使用AI辅助查阅工程中的Dockerfile、构建配置和接口契约，制定可验证的更新步骤；不得自行删除数据库卷来处理构建问题，不得修改冻结数据或权限机制绕过报错。教师不要求完全断网重建或任意新增依赖。

A3. 安装、初始化和运行的验收底线

  • 环境：Docker Engine有Server响应、OSType=linux、Compose可用；WSL2后端确认；其他课程的容器和卷不受影响。
  • 文件与镜像：学生包校验通过，离线镜像标签和平台正确；不要将镜像归档、私密密钥或Docker数据卷提交GitHub。
  • 初始化：已导入正式课堂数据，电影8,459部、历史匿名用户5,000名、历史评分798,775条；初始化返回成功状态。
  • 运行：db/api/web健康，电影查询、注册登录和评分/收藏保存成功；停止与再次启动后数据仍在。
  • 教学起点：热门、内容、ItemCF、ALS、冷启动等算法接口初始为501“尚未实现”，这是等待学生开发的状态；推荐实验室页面也可能保留占位提示。

遇到端口占用、Docker无法启动、镜像缺失、密钥不完整、旧数据库卷、构建失败或下载失败时，按照当前发行包的详细安装指南停止并记录错误；不要使用docker compose down -v、docker volume prune、docker system prune、重置WSL或恢复Docker出厂设置作为常规修复办法。

课时安排：实验一首先确保每组至少一台电脑具备可运行Starter Kit的条件；环境问题由教师集中分流，小组在课堂内继续开展算法学习。所有安装与开发均按六次课堂时间安排，不另设课后作业。

附录B　GitHub小组协作与六次提交（课堂内必做）

  1. 实验一建库：每组创建一个GitHub私有仓库，邀请组员协作，并邀请组员、向教师开放仓库查看权限；推荐先将教师Starter Kit保存为初始版本，再进行个性化修改。
  2. 每次课提交：每次实验结束前，在仓库中形成能反映该次任务进展的提交并推送到GitHub。允许尚未完成的模块，但应明确记录已完成内容、真实测试状态和待解决问题；不得伪称通过验收。
  3. 推荐工作流：先查看git status，检查变更，再git add、git commit、git push；多人协作先同步主分支，避免覆盖其他组员的工作。建议按lab1至lab6使用标签或在README中记录阶段版本。
  4. 保护数据：不得上传.env、密钥、密码、个人令牌、数据库卷、真实登录Cookie、node_modules、虚拟环境、大型模型工件及教师参考答案。正式MovieLens/TMDB文件按课程授权与教师发布规则处理；仓库通过说明与本地导入脚本引用数据包，不把整套数据库推到GitHub。
  5. 课堂验收：教师检查仓库可访问性、最新提交和实际系统成果，不以提交次数、代码行数或AI生成比例代替个人贡献评价。

最低证据：每次课在教师课堂通知的提交入口提供本次commit ID或GitHub链接（未公布固定网址时不自行猜测），并现场展示任务结果。GitHub暂时无法访问时，先保留本地Git提交并记录错误，课堂内经教师确认后处理，不因网络故障删除成果。

附录C　公网部署（挑战版可选扩展）

目标：在保持核心业务和数据安全的前提下，使外部设备可通过HTTPS访问团队作品，并能够演示至少一条真实推荐链路。无需自购服务器，不允许通过暴露个人电脑数据库端口来冒充线上部署。

可自行选择合规且费用可控的平台；优先使用免费或校内已有资源。允许采取“线上演示前端＋受控后端API”架构，但只有静态页面、假电影数据或无法调用真实推荐结果时，不算完成系统部署。

验收条件：提供可访问URL（或教师可访问的受控演示地址）、部署架构简图、运行环境与启动说明，并现场证明HTTPS访问、登录/电影查询/推荐流程、数据库不对公网暴露、密钥由平台安全配置、错误状态不泄露内部信息。不得上传完整训练/测试评分或个人数据到未经批准的服务，不得在公网使用默认口令或开放MySQL 3306。

公网部署属于挑战版的一种可选创新：不替代基础版，不替代标准版三选二，也不要求所有小组付费或课后维护服务。无法获得合适云资源的小组可选择其他同等挑战方向。
